## 一、必须遵循的技术事实

Claude Code Plugin 的 shell 可执行安装方式为：

```bash
claude plugin install superpowers@claude-plugins-official
```

不要把交互式 slash command 当作 shell 命令：

```text
/plugin install ...
```

服务端必须调用真实可执行文件 `claude`，并通过参数数组启动子进程：

```python
[
    claude_binary,
    "plugin",
    "install",
    "superpowers@claude-plugins-official",
]
```

禁止：

```python
shell=True
os.system(...)
subprocess.run("claude plugin install ...", shell=True)
```

Claude Code Plugin 官方文档：

```text
https://code.claude.com/docs/zh-CN/plugins
```

插件装配后，Claude Code 应通过工作空间中的不可变插件包启动，例如：

```bash
claude \
  --plugin-dir ./superpowers@claude-plugins-official@sha256-<digest>
```

实际目录名称需要包含解析后的 package、marketplace 和制品摘要，例如：

```text
superpowers@claude-plugins-official@sha256-01ab...
```

不得使用字面量 `@sha256` 代替真实摘要。

## 二、架构纠偏

### 1. 删除错误的 AgentRunOptions 设计

当前以下设计是错误的：

```text
AgentRunOptions.settings_json
AgentRunOptions.claude_settings_json
AgentRunOptions.local_plugin_paths
```

这些字段不属于单次 Agent Run 的业务参数，必须从以下链路中移除：

- `AgentRunOptions`
- ClaudeAgent request model
- Deck Chat context
- Agent service
- Agent runner
- Claude SDK options 装配
- 前端 request body
- 相关测试和文档

同时禁止使用以下方式作为 Deck 插件主加载路径：

```python
ClaudeAgentOptions(
    settings=...,
    plugins=[{"type": "local", "path": "..."}],
)
```

也不能由 Deck Chat 动态构造：

```json
{
  "enabledPlugins": {
    "plugin-id": true
  }
}
```

原始需求只是：

> 在公共工作空间中安装和配置 Claude Code Plugin，并在发起 Deck 对话时，将选定插件的不可变文件包复制到当前 ClaudeAgent 工作空间，再通过 Claude CLI 的 `--plugin-dir` 加载。

### 2. 正确分层

系统应拆成以下边界：

```text
Settings / Plugin Admin
    ↓
公共插件安装工作空间
    ↓
Claude CLI plugin install
    ↓
公共不可变插件制品仓库
    ↓
Deck 保存插件引用
    ↓
创建 Deck Chat
    ↓
把插件包复制到当前 Agent workspace
    ↓
claude --plugin-dir ./<immutable-plugin-dir>
```

职责如下：

| 模块 | 职责 |
|---|---|
| Plugin Admin | 输入插件包名、发起安装、查看安装结果 |
| 公共插件工作空间 | 使用真实 Claude CLI 安装插件 |
| 公共插件制品仓库 | 保存精确版本、manifest、文件和 digest |
| Deck | 配置需要使用的插件引用，不保存工作流 |
| Dream | 选择 Deck、发起对话、处理 Agent 产出和审阅 |
| Agent Workspace Builder | 把 Deck 插件包复制到当前 Agent workspace |
| Claude CLI Launcher | 根据 workspace launch manifest 添加 `--plugin-dir` |
| AgentRunOptions | 只保存真正的单次 Agent 参数，不保存插件路径或 settings JSON |

## 三、公共插件工作空间

实现服务端管理的公共插件安装工作空间，例如：

```text
<managed-runtime-root>/
├── install-workspace/
│   └── .claude/
├── registry/
└── artifacts/
    └── superpowers@claude-plugins-official@sha256-<digest>/
        ├── .claude-plugin/
        │   └── plugin.json
        ├── skills/
        ├── commands/
        ├── agents/
        ├── hooks/
        └── ...
```

具体文件结构必须以官方文档和真实 CLI 安装结果为准，不得凭空设计。

公共工作空间必须：

- 由服务端创建和管理；
- 与开发者真实 `~/.claude` 隔离；
- 使用 Claude Code 官方支持的配置目录和作用域；
- 有明确的运行路径和 `cwd`；
- 不允许浏览器提交本地文件路径；
- 不允许插件包逃逸出受管根目录；
- 不通过 symlink 指向用户数据；
- 保存安装 operation ID；
- 保存真实 CLI exit code；
- 保存脱敏后的 stdout/stderr；
- 保存 CLI 版本；
- 保存安装前后文件变化；
- 保存 plugin manifest；
- 保存解析版本和 SHA-256；
- 安装失败时不得生成 ready 记录。

## 四、安装流程

用户在 Settings → Plugins 点击 `Install Plugin`，输入：

```text
superpowers@claude-plugins-official
```

后端执行：

```python
subprocess_exec(
    [
        claude_binary,
        "plugin",
        "install",
        "superpowers@claude-plugins-official",
    ],
    cwd=managed_install_workspace,
    env=isolated_claude_environment,
)
```

要求：

1. 校验 package spec。
2. 禁止 shell 元字符和命令注入。
3. 验证 Claude CLI 路径。
4. 记录 `claude --version`。
5. 使用明确的公共安装 workspace。
6. 设置超时。
7. 捕获退出码。
8. 检查 CLI 实际写入的 registry 和插件目录。
9. 找到插件根目录。
10. 校验 `.claude-plugin/plugin.json`。
11. 枚举插件包含的 skills、commands、agents、hooks、MCP 或其他官方支持内容。
12. 计算整个目录的确定性 SHA-256。
13. 将插件复制到不可变 artifact 目录：

```text
<package>@<marketplace>@sha256-<digest>
```

14. 保存数据库安装记录。
15. 将状态标记为 `ready`。
16. 同一 package、解析版本和 digest 重试时返回原安装结果。

不得仅修改数据库来伪造安装成功。

## 六、Deck 配置

Deck 只保存公共插件安装记录的引用：

```text
deck_id
plugin_installation_id
package_spec
resolved_version
artifact_digest
enabled
order_index
```

Deck 不保存：

- 本地绝对路径；
- `settings_json`；
- `local_plugin_paths`；
- Workflow；
- Workflow Preflight；
- Workflow Run；
- Claude SDK plugin options。

Deck Editor 只能选择：

- 已真实安装；
- 状态为 ready；
- digest 校验通过；
- 与当前 Claude Code 版本兼容的插件。

## 七、发起 Deck Chat 时的装配流程

发起 Deck 对话时：

1. 根据 thread 创建当前 ClaudeAgent workspace。
2. 读取 thread 已锁定的 Deck。
3. 读取 Deck 已启用的插件安装引用。
4. 从公共 artifact 仓库加载精确 digest 对应的插件。
5. 重新校验 manifest 和 digest。
6. 将插件目录复制到当前 Agent workspace，例如：

```text
<agent-workspace>/
├── .ink/
│   └── plugins/
│       └── superpowers@claude-plugins-official@sha256-<digest>/
└── ...
```

7. 保持官方插件根目录结构完整，尤其是：

```text
.claude-plugin/plugin.json
skills/
commands/
agents/
hooks/
```

8. 创建服务端控制的 launch manifest，例如：

```json
{
  "schema_version": "claude-launch/v1",
  "plugins": [
    {
      "package_spec": "superpowers@claude-plugins-official",
      "relative_path": ".ink/plugins/superpowers@claude-plugins-official@sha256-<digest>",
      "artifact_digest": "sha256:<digest>"
    }
  ]
}
```

9. Claude CLI Launcher 从当前 workspace 读取该受控 manifest。
10. 启动 Claude CLI 时追加：

```bash
--plugin-dir ./.ink/plugins/superpowers@claude-plugins-official@sha256-<digest>
```

11. 多个插件必须生成多个独立 `--plugin-dir` 参数，具体格式以官方 CLI 实际行为为准。
12. 返回插件加载 receipt。

禁止客户端提交 `--plugin-dir`，也禁止客户端控制 launch manifest。

## 八、AgentRunOptions 的正确边界

`AgentRunOptions` 应只保留真正的运行参数，例如：

```text
model
max_turns
cwd
permission_mode
tool_choice
system_prompt
attachments
resume/session 信息
```

不得包含：

```text
settings_json
claude_settings_json
local_plugin_paths
enabled_plugins
plugin package spec
plugin installation path
plugin artifact path
```

插件准备属于 workspace bootstrap 阶段。

推荐执行顺序：

```text
DeckChatContextResolver
→ WorkspacePluginPacker
→ WorkspaceLaunchManifestWriter
→ ClaudeCliLauncher
→ Agent Session
```

如果 ClaudeAgent SDK 默认隐藏底层 CLI 参数，应在 CLI process launcher/adapter 边界增加 `--plugin-dir`，不要重新把路径塞回 `AgentRunOptions`。
