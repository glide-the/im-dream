> 本文是用户可见 Calendar 日记日期弹窗的现行产品合同。当前改版只调整页面容器和信息层级；Task、Thread、Run、Tool、revision、幂等、恢复与执行状态继续使用既有系统合同。

## 0. 证据与设计判断

### 0.1 输入能够证明的事实

- 用户目标截图展示一张独立的 Paper Cream 内容卡：卡片顶部为日期标题“今天”和数量“1篇”，标题区与条目区之间有一条横向分隔线；正文只有一条日记时，也保留完整卡片边界。
- 截图中的日记条目是卡内的轻量圆角行：左上显示时间和“当前笔记”胶囊标识，标题另起一行，删除入口靠右；当前日记以绿色细边框和极浅绿色底表达。
- 用户明确要求 Calendar 右栏中的 `Scheduled tasks` 与 `Diary` 是两个同级、各自独立的卡片，不能继续放在一个大容器内仅靠标题和分隔线分组。
- 现行 `CalendarPopup.tsx` 把日期摘要、定时任务区和日记区放在同一个 `.calendar-popup__workspace` 中；`.calendar-popup__section + .calendar-popup__section` 只用顶部分隔线区分两个内容类型。这正是本轮需要修正的结构。
- 现行代码已经拥有任务加载、失败、重试、空态、任务操作、编辑、历史、撤销、执行状态刷新、日记打开和日记删除能力。本轮只改变信息架构与呈现容器，不改变这些业务能力。
- `Ink & Memory UI Design v2.1` 给出 Warm Canvas、Paper Cream、Charcoal Brown、Body Brown、Warm Brown、Muted Tan、Border Paper 等语义色；同时要求减少多层面板、静止时避免重阴影、以留白和分隔线表达层级。

### 0.2 冲突处理

用户对本页面提出的“两张独立卡片”是明确页面需求，优先于 PDF 中面向全站普通内容的“减少卡片”一般规则。实现方式应控制在**两个分类级纸面容器**：右栏不再增加包裹两类内容的第三张大卡；卡内条目只使用细边框、浅底和留白，静止时不使用悬浮重阴影。这样既满足分卡要求，也避免多层卡片堆叠。

### 0.3 待后续阶段确认的内容

- 输入没有证明分类卡必须使用固定像素高度；应由内容和现有弹窗可用空间决定。
- 输入没有证明任务卡和日记卡必须等高；默认按内容自然高度排列。
- 输入没有证明应新增折叠、拖拽、排序或新建入口；本轮不增加。
- PDF 是品牌视觉规范，不是 Calendar 专用交互稿；只采纳其中可复用的颜色、字体、分区和阴影规则。

## 1. 背景与问题

Calendar 弹窗当前在右侧使用一个带边框的大容器，顶部放日期摘要，下方依次放 `Scheduled tasks` 和 `Diary`。两个业务对象只靠标题、间距和横线区分，用户会把它们理解为同一张详情面板中的连续段落，无法形成“任务配置/运行结果”和“日记内容”两类明确心智模型。

本轮将右栏改为透明的纵向工作区，在其中排列两个同级纸张卡片：定时任务卡和日记卡。每张卡片独立承担自己的标题、数量、分隔线、内容与局部状态。任务接口失败时只改变任务卡，日记卡仍可读、可打开、可删除。

## 2. 目标与边界

### 2.1 目标

1. 用户不阅读条目内容也能从两个独立轮廓识别 `Scheduled tasks` 与 `Diary`。
2. 每张卡片的标题、计数、分隔线和状态反馈都有清楚归属。
3. 保留已有任务操作、历史、错误恢复、Thread 跳转以及日记打开/删除能力。
4. 任务卡加载或失败时，日记卡保持正常显示和操作。
5. 宽屏维持月历与右栏并排；窄屏按月历、任务卡、日记卡顺序堆叠。
6. 视觉遵循 Ink & Memory 暖纸色、炭棕文本、纸边细线、充足留白和无重阴影原则。

### 2.2 非目标

- 不新增独立定时任务页面，也不把创建入口移入 Calendar；创建仍通过现有 Chat Tool。
- 不改变任务定义状态、执行状态、revision、幂等、并发、历史或 Thread/Run 关系。
- 不改变日记数据来源、打开和删除语义。
- 不新增折叠卡、拖拽排序、任务/月摘要标记、复杂 Cron 或工作流编排。
- 不用浏览器计算下一次执行时刻、重试结果或服务器状态。
- 不为视觉调整新增确认弹窗。

## 3. 页面模块结构（自上而下、自左至右）

| 区块编号 | 模块名 | 位置与形态 | 内容 | 主要职责 |
| --- | --- | --- | --- | --- |
| A1 | Calendar 弹窗 | 遮罩层上的暖纸浮层 | 弹窗标题、关闭入口、月历与选中日工作区 | 约束焦点与整体滚动范围 |
| A2 | 月历纸面 | 宽屏左栏；窄屏第一段 | 月份导航、星期、日期网格、今天/选中日/日记标记 | 选择需要查看的日期 |
| B1 | 右栏卡片栈 | 宽屏右栏；无共享外框的纵向容器 | 选中日期提示、B2 与 C1 | 安排两张同级卡片及右栏滚动 |
| B2 | Scheduled tasks 卡片 | 卡片栈第一张独立 Paper Cream 卡片 | B3 卡头、B4 内容区 | 展示当日任务定义、运行状态和操作 |
| B3 | Scheduled tasks 卡头 | B2 顶部 | 日期/分组标题、任务数量、需处理数量（有值时） | 明确任务卡身份和摘要 |
| B4 | Scheduled tasks 内容区 | B3 下方，以 Border Paper 分隔 | 加载、错误/重试、空态、任务列表、局部提示 | 承载任务现有完整业务能力 |
| B5 | 任务条目 | B4 内部轻量条目 | 标题、定义状态、计划、下一次执行、最近结果、主要操作、更多菜单 | 操作一个任务；编辑和历史仍归属该条目 |
| C1 | Diary 卡片 | 卡片栈第二张独立 Paper Cream 卡片 | C2 卡头、C3 内容区 | 展示当日日记，保持与任务的类型边界 |
| C2 | Diary 卡头 | C1 顶部 | 日期/分组标题、日记数量 | 明确日记卡身份和数量 |
| C3 | Diary 内容区 | C2 下方，以 Border Paper 分隔 | 空态或日记列表 | 打开和删除日记 |
| C4 | 日记条目 | C3 内部轻量圆角行 | 时间、当前笔记标识、首行标题、删除入口 | 打开一篇日记；删除对应日记 |

### 3.1 布局顺序

```text
桌面：
┌──────────────────────── Calendar 弹窗 ────────────────────────┐
│  ┌──────── A2 月历纸面 ────────┐   B1 右栏卡片栈（无外框）      │
│  │ 月份导航 / 星期 / 日期网格  │   ┌─ B2 Scheduled tasks ───┐ │
│  │                            │   │ B3 标题 / 任务数        │ │
│  │                            │   ├─────────────────────────┤ │
│  │                            │   │ B4 状态或 B5 任务条目   │ │
│  │                            │   └─────────────────────────┘ │
│  │                            │   ┌─ C1 Diary ──────────────┐ │
│  │                            │   │ C2 标题 / 日记数        │ │
│  │                            │   ├─────────────────────────┤ │
│  │                            │   │ C3 空态或 C4 日记条目   │ │
│  └────────────────────────────┘   └─────────────────────────┘ │
└────────────────────────────────────────────────────────────────┘

窄屏：A2 月历纸面 → B2 Scheduled tasks 卡片 → C1 Diary 卡片
```

关键结构约束：

- B2 与 C1 必须是 DOM 和视觉上的同级独立区域，各自有圆角边界与背景。
- B1 只负责网格/纵向间距和滚动，不绘制包住 B2、C1 的背景、边框或阴影。
- B2、C1 的卡头和内容区之间各自绘制完整分隔线；不能用一条横线同时承担两个卡片的分区。
- 两张卡之间保留可见的 Warm Canvas 间隙，使用户能看到两个完整外轮廓。

## 4. 详细功能需求

### 4.1 选中日期与摘要归属

1. 选择月历日期后同时刷新 B2 和 C1 的内容。
2. 选中日期可作为 B1 上方不带卡片外框的简短上下文，也可分别进入两个卡头；不得恢复成包裹两张卡的共享摘要面板。
3. 任务数只能出现在任务卡头，日记数只能出现在日记卡头。任务数未知时显示任务卡局部的“数量未知”，不能使日记计数变为未知。
4. `failed` 或 `state_unknown` 的需处理数量属于任务卡头；激活后焦点移动到任务卡内第一条相关任务。

### 4.2 Scheduled tasks 独立卡片

1. 卡头使用手写感标题字体和 Charcoal Brown；数量使用次级文字或轻量计数徽标。
2. 卡头下方用 Border Paper 细线分隔内容区。
3. 已认证用户选中日期后，任务卡始终保留自己的内容区域，并在其中互斥显示：
   - 加载态：结构与任务条目相近的轻量骨架或明确加载文案；
   - 失败态：卡内 inline alert、可行动说明和“重试”；
   - 空态：清楚说明当日没有定时任务；
   - 内容态：一条或多条任务条目。
4. 任务接口失败不得隐藏 Diary 卡片，不得用覆盖右栏的全局错误替代卡内错误。
5. B5 继续展示现有标题、定义状态、计划、时区、下一次执行、最近结果、立即运行、暂停/恢复、更多菜单、编辑、历史、删除/撤销和打开执行会话能力。
6. 编辑面板和历史面板在所属 B5 内展开；它们不能成为与 B2、C1 同级的第三类卡片。
7. 多条任务按现有服务端/前端顺序呈现，本轮不新增排序规则。
8. 卡内自动刷新暂停、操作失败、revision 冲突、DST 错误和状态待核查反馈继续局部显示，不改变现行语义。

### 4.3 Diary 独立卡片

1. C1 无论是否有日记都保持完整独立纸面轮廓；空态显示在 C3 内。
2. 卡头展示本地化日期或 `Diary` 标题以及日记数量；标题和数量属于同一卡头。
3. C4 采用目标截图的信息层级：
   - 左侧第一行：时间；当前打开的日记紧随其后显示“当前笔记”文字徽标；
   - 左侧第二行：日记首行标题，过长时按现有可用宽度截断；
   - 右侧：删除入口，名称包含日记标题；
   - 点击非删除区域打开日记。
4. 当前日记同时用文字徽标与绿色细边/浅底表达，不能只靠颜色。
5. 普通日记条目使用 Border Paper 细边、Paper Cream/Solid Cream 浅底和圆角；静止时不使用悬浮重阴影。
6. 任务卡加载、失败、编辑或历史展开不禁用日记卡。

### 4.4 局部状态与恢复

| 状态 | Scheduled tasks 卡片 | Diary 卡片 |
| --- | --- | --- |
| 初始加载 | 卡头保留，内容区显示加载反馈 | 已有日记正常显示 |
| 任务 API 失败 | 卡内错误 + 重试；数量显示未知 | 不变，仍可打开/删除 |
| 无任务 | 卡内空态 | 不变 |
| 有任务 | 显示任务条目和现有操作 | 不变 |
| 无日记 | 不变 | 卡头计数为 0，内容区显示空态 |
| 日记删除失败 | 不变 | 对应现有删除错误反馈，不改变其他日记 |
| 任务操作失败 | 对应任务条目局部反馈，不乐观伪造成功状态 | 不变 |


### 4.5 业务交互时序

#### 时序 A：选择日期并分别读取任务与日记

~~~mermaid
sequenceDiagram
    actor U as 用户
    participant C as CalendarPopup
    participant D as 日记数据接口
    participant S as Scheduled Task API
    participant A as Admin 数据能力

    U->>C: 选择日期
    par 读取日记
        C->>D: 查询该日日记
        D-->>C: diary entries 或日记局部错误
    and 读取任务
        C->>S: GET scheduled-tasks(date)
        S->>A: 读取定义和最近执行
        A-->>S: task/trigger DTO 或明确错误
        S-->>C: 任务列表或任务局部错误
    end
    C-->>U: Scheduled tasks 独立卡 + Diary 独立卡
    Note over C,U: 任一请求失败只替换所属卡片正文
~~~

#### 时序 B：立即运行并形成独立执行记录

~~~mermaid
sequenceDiagram
    actor U as 用户
    participant C as CalendarPopup
    participant API as Dream Scheduled Task API
    participant A as Admin 调度数据服务
    participant W as Dream Scheduler Worker
    participant T as 既有 Chat/Thread 执行入口

    U->>C: 点击 Run now
    C->>API: 使用稳定请求键提交手动触发
    API->>A: 创建或返回同一 manual trigger
    A-->>API: trigger=queued
    API-->>C: 已加入执行队列
    W->>A: claim + prepare
    A-->>W: claim_id + 短期 authority
    W->>T: 通过公开生产入口创建新 Thread 并执行 turn
    T-->>W: 流式执行结果
    W->>A: 记录 target_thread_id、Run 结果与终态
    C->>API: 有界刷新定义和历史
    API-->>C: 最近执行 + 历史
    C-->>U: 在所属任务条目显示结果和打开会话入口
~~~

#### 时序 C：编辑 desired 并以 revision 提交

~~~mermaid
sequenceDiagram
    actor U as 用户
    participant C as CalendarPopup
    participant API as Dream Scheduled Task API
    participant A as Admin 调度数据服务

    U->>C: 展开编辑并修改 desired
    C->>API: 更新任务 + 当前 revision
    API->>A: 校验权限、规则、时区与 revision
    alt revision 匹配且输入合法
        A-->>API: 新 effective + revision
        API-->>C: 保存成功
        C-->>U: 以服务端 effective 更新卡片
    else revision 冲突或输入无效
        A-->>API: 最新 effective / 字段错误
        API-->>C: 明确失败
        C-->>U: 保留 desired，展示差异或字段错误
    end
~~~

### 4.6 定义状态、执行状态与可用动作

| 定义状态 | 可用动作 | 页面表达 |
| --- | --- | --- |
| active | 立即运行、暂停、编辑、历史、删除 | 显示下次执行与最近结果 |
| paused | 恢复、编辑、历史、删除 | 不显示旧的下一次执行；恢复后采用服务端新值 |
| exhausted | 立即运行、历史、删除 | 单次计划已完成，不提供编辑重新排期 |
| deleted | 撤销删除 | 原位置折叠为撤销条；已开始的运行不被取消 |

| 最近执行状态 | 用户可见含义 | 处理 |
| --- | --- | --- |
| queued/claimed/preparing/running | 已排队、准备或执行中 | 有界刷新；不伪造成功 |
| succeeded | 已完成 | 展示完成时间；有 target_thread_id 时允许打开会话 |
| failed | 执行失败 | 显示可行动反馈；不改变未来计划 |
| state_unknown | 结果需要核查 | 禁止盲目重复运行；保留原请求键并提供核查路径 |
| skipped | 本次未执行 | 展示服务端原因，不改写定义状态 |


## 5. 视觉要求

### 5.1 色彩与材质

- 弹窗与卡片间隙使用 Warm Canvas / 现有应用背景 token。
- B2、C1 使用 Paper Cream；菜单、输入或需要不透明承载的局部控件使用 Solid Cream。
- 标题使用 Charcoal Brown，正文使用 Body Brown，辅助信息使用 Warm Brown 或 Muted Tan。
- 卡片边框与卡头分隔线使用 Border Paper。
- 当前日记的绿色只作为小面积状态信号，沿用现有成功/绿色语义 token；不得大面积铺色。
- 不新增孤立十六进制色值；生产实现使用仓库现有语义 token 与 `color-mix`。

### 5.2 形状、留白与阴影

- B2、C1 使用一致的轻纸面圆角和一层细边框。
- 两卡间距落在 PDF 建议的 12–24 px 视觉节奏内，最终值应复用现有 spacing 体系并根据可读性确定。
- 卡头具有清楚的上下内边距，标题和计数不贴边；内容区与卡头通过完整分隔线分开。
- 卡片静止时无悬浮重阴影；如现有浮层需要空间分离，只允许极轻暖棕阴影。
- 卡内条目之间以间距或细分隔线区分，避免每层都出现强边框和阴影。

### 5.3 字体与动作层级

- 分类标题沿用 Excalifont / Xiaolai / Georgia 的手写感回退链。
- 任务与日记正文沿用现有 UI 正文字体，保证时间、状态与操作清晰。
- 主操作维持现有 Action Brown 层级；次要操作、链接和危险操作维持现有语义色。
- 不因分卡而增加新的装饰图标或无业务意义文案。

## 6. 响应式与滚动

1. 宽屏维持月历在左、右栏卡片栈在右；右栏卡片栈独立滚动。
2. 中等宽度允许任务事实和操作换行，但两个分类卡仍保持独立外轮廓。
3. 窄屏按 A2 → B2 → C1 单列堆叠，卡片占满可用宽度，不产生横向滚动。
4. 卡头不得因窄屏而与内容脱离；标题与计数可换行或收拢，但不能移到共享摘要区。
5. 任务编辑和历史展开增加 B2 高度，由 Calendar 详情滚动区承载；背景页面不得跟随滚动。
6. 现有触控尺寸、焦点环和 reduced-motion 行为继续适用。

## 7. 可访问性

1. B2 与 C1 分别使用可识别的 `section`，并通过各自可见标题建立 `aria-labelledby`。
2. 卡头数量变化使用合适的 `aria-live="polite"` 语义；任务错误保留 `role="alert"`。
3. 两张卡的 DOM 顺序与视觉顺序一致：任务在前、日记在后。
4. 键盘焦点顺序先经过任务卡可用操作，再进入日记条目；任务错误重试后焦点保持可预测。
5. 日记条目打开按钮和删除按钮保持独立可访问名称与点击区域。
6. 当前日记、任务定义状态和执行状态均包含文字，不能只用色边表达。

## 8. 技术建议

1. 在现有 `CalendarPopup` 内重组结构：把 `.calendar-popup__workspace` 从有背景/边框的大面板改为无视觉外框的卡片栈；将任务区与日记区分别赋予独立的 paper-card 结构类。
2. 复用现有 `ScheduledTaskCard`、任务 API、状态管理、历史、编辑、事件刷新、i18n、日记读取/删除函数；不要新增第二套请求或状态机。
3. 将任务加载/失败/空态条件放入 B2 内。避免当前条件在“加载完成且任务为 0”时整个任务区消失，从而使已有空态分支不可见。
4. B2、C1 的标题 ID 保持唯一，并继续服务现有 section 语义；测试应按语义与结构定位，避免只断言屏幕上出现文本。
5. 样式只消费当前主题 token。不要硬编码业务 ID、主机、路径、任务阈值或状态策略。
6. 保持日记与任务的状态隔离：任务异常不能清空 `selectedEntries`，日记操作也不能触发任务定义重置。

## 9. 验收条件

- [ ] 右栏不存在同时包住 Scheduled tasks 和 Diary 的可见大卡边框、背景或阴影。
- [ ] Scheduled tasks 与 Diary 是两个同级独立 section，均有各自 Paper Cream 背景、圆角外框、标题、计数、分隔线和内容区。
- [ ] 两卡之间可见 Warm Canvas 间隙，轮廓不会连成一张大卡。
- [ ] 任务加载、失败、重试、空态和列表全部发生在 Scheduled tasks 卡内。
- [ ] 任务 API 失败时 Diary 卡仍显示并可打开、删除日记。
- [ ] Diary 空态发生在 Diary 卡内；有数据时条目遵循“时间/当前笔记 + 第二行标题 + 右侧删除”的目标层级。
- [ ] 当前日记同时有文字徽标与绿色细边/浅底反馈。
- [ ] 现有任务的立即运行、暂停/恢复、编辑、历史、删除/撤销、打开会话及失败反馈未丢失。
- [ ] 宽屏为左月历/右卡片栈；窄屏按月历、任务卡、日记卡堆叠，无横向溢出。
- [ ] 静止卡片和条目无重阴影，色彩与边框只使用现有 Ink & Memory 语义 token。
- [ ] 自动化测试能通过独立 section/标题关系和不同父卡片断言两卡分离，而不是只检查标题文字存在。
