## 背景与问题

用户在 Dream Agent 生成回复期间仍需继续输入。新消息应先由服务端持久化并进入当前 Thread 的输入队列，再以卡片显示在原聊天输入框上方。用户可从卡片调整方向、取消、编辑，或将该消息作为独立 Thread 的首条输入在侧边聊天中打开。页面保留 Dream 现有深棕底色、暖色描边和手写字体的视觉语言；参考图提供**结构与动作**，不要求照搬黑灰蓝配色或另一产品的控件。

当前故障图标出的三处问题如下。图中位置、文案和裁切是可观察事实；代码原因单独列出，服务端不可用原因仍需以受权接口回执确认。

## 目标与边界

1. 运行中的输入仍能编辑与提交；服务端成功接收后显示排队卡片。前端断开或刷新不代表当前 Claude 轮次停止，刷新后从服务端恢复队列与运行状态。
2. 卡片紧贴聊天输入 Dock 上沿，正文、状态、主操作、删除及更多菜单明确可见。Dock 右端的发送/停止共用一个操作位，完整落在安全区域。
3. 队列不可用、提交失败、结果不明分别给出符合服务端事实的反馈；不把失败草稿画成 `queued`，不因页面重试重复消费消息。
4. 复用 Dream 原聊天页面、输入组件、消息列表、状态查询和语义色 token。不新增独立聊天页面、外部 CDN、产品无关确认弹窗或内部会话 ID 展示。

## 概念与业务规则

`draft` 是尚在输入框内、未经服务端确认的内容。它不是队列消息；前端可保存草稿和本次提交标识。`message_id` 标识已持久化的消息，`queue_sequence` 确定消费顺序，`revision` 用于校验针对当前状态的操作。同一 Thread 至多一个消费中的 Claude 轮次。前端显示的“排队中”“已消费”须对应服务端持久化状态，不能由动画、SSE 单帧或本地计时推断。

| 服务端消息状态 | 卡片显示 | 可执行动作 | 转换依据 |
| --- | --- | --- | --- |
| `queued` | 正文、排队中；多条按 `queue_sequence` 排序 | 调整方向、删除、菜单内编辑/在侧边聊天中打开/关闭排队 | 仅在服务端仍确认 `queued` 且 revision 匹配时接受变更。 |
| `selected` | “已选中，等待切换”；留在卡片列 | 查看，不重复选取或取消 | 服务端完成选中持久化；不等于 Claude 已收到消息。 |
| `dispatching` | “正在发送”；留在卡片列 | 查看 | 服务端取得该消息并开始唯一派发；失败时不能凭前端超时自动重发。 |
| `consumed` | 不再作为待处理卡片显示；历史消息仍可见 | 无排队操作 | 服务端确认 SDK 接收及消费结果并持久化。 |
| `cancelled` | 从待处理卡片列移除；原历史消息依既有规则保留 | 无排队操作 | 服务端取消当前消息的排队消费。 |
| `failed` | 显示失败原因及适当后续动作；不标记“排队中” | 根据服务端返回可重试或查看状态 | 明确的失败终态与持久化结果。 |
| `state_unknown` | “状态待核对”，不显示为成功入队或已消费 | 刷新状态；不自动重发 | 运行 owner 丢失、请求超时或结果无法核实时由服务端给出。 |

### 输入、卡片与错误流程

1. 用户在 Agent 运行中输入并点击发送。输入组件暂时清空本次草稿，使用同一消息提交标识调用既有受权入口；只有成功回执确认消息已保存和 `queued` 后才添加卡片。失败则恢复草稿，结果不明则保留原提交标识供状态核对。连续发送形成多张独立卡片；同一标识重试只对应同一条消息。
2. 用户仅发送而不选取时，卡片保持 `queued`。当前回复继续运行；轮次结束后同一 Thread 的运行 owner 按 `queue_sequence` 派发下一条。卡片状态由服务端数据变化驱动。
3. 用户点击“调整方向”时，服务端先校验状态和 owner，再执行受控中断/选中流程。界面先展示服务端确认的 `selected`，只有 SDK 与持久化回执确认后才展示 `dispatching` 或 `consumed`；中断失败显示具体错误，其他排队卡片保持原位。
4. 垃圾桶与“关闭排队”语义相同：只取消**当前选中卡片**所代表的 `queued` 消息并移除该卡片。无需确认弹窗；版本冲突时重读状态，不移除其他卡片。
5. “编辑消息”仅用于仍为 `queued` 的卡片。编辑时卡片内显示正文输入框；提交后由服务端取消旧队列条目并以新消息 ID 排到尾部。失败时保留编辑稿，并查询旧消息状态，不猜测取消是否成功。
6. “在侧边聊天中打开”仅用于仍为 `queued` 的卡片。服务端原子取消其在原 Thread 的排队消费，创建独立 Dream Thread，以该正文作为首条输入；回执给出业务任务/新 Thread 后打开右侧聊天。原 Thread 不再消费该消息；重复点击不创建第二个任务。
7. 若查询队列失败，只显示“队列暂时不可用”及刷新状态动作，已输入的草稿仍在输入框内；若提交明确失败，保留正文与提交标识并显示“重试发送”；若提交结果不明，先按该标识查服务端状态，不能直接换 ID 重发。错误反馈不占用或伪造排队卡片。

## 视觉与响应式规则

- Dream 的深棕背景、暖色描边、手写字与现有按钮尺寸关系保持一致；状态用现有语义 token 表达，不直接照搬参考图的蓝色、灰色或硬编码屏幕坐标。
- 卡片和 Dock 在同一个 Chat 内容宽度约束下对齐。卡片最小化垂直间距；长正文截断显示，同时提供展开或可访问完整文本。状态、主操作和菜单在常用窗口宽度下不互相覆盖。
- Dock 右侧仅有一个操作位；左侧设置与中间内容可伸缩。输入内容为空且主轮次运行时显示停止；输入内容非空时切换为发送，发送成功并清空草稿后重新显示停止。发送失败恢复草稿后继续显示发送。侧栏展开、窗口缩窄、浏览器缩放或多行输入时，当前按钮仍完整位于 Dock 内。按钮点击区域和键盘焦点可辨认。
- 窄屏时卡片可将状态/操作移到第二行或收进菜单；保留正文和必要操作，不能把卡片横向推出屏幕。菜单选择能通过键盘和读屏执行，关闭后焦点回到触发按钮。
- 错误反馈跟随 Chat 主列，而不是固定到浏览器视口。文案使用当前界面语言；队列不可用与运行停止属于不同状态，不共享一个“停止”提示。

## 实现映射与发布边界

- `ChatPanel` 承接当前 Thread 队列查询、错误反馈和原聊天流；`AIInputDock` 承接草稿与单一发送/停止操作位；`ThreadInputQueueCard` 承接每条消息操作。组件不得复制第二套聊天页面。浏览器自动化测量 Dock 与当前可见按钮的位置，覆盖宽屏、窄屏和宽视口中的窄列。
- 队列操作传稳定 `message_id` 与当前 `revision`。请求或 SDK 结果不确定时保留原消息标识，先查询服务端状态；前端重连和侧边聊天读取不重新触发推理。权限拒绝、Admin capability 不可用和运行 owner 丢失分别给出合适反馈。
- 英文和中文反馈来自现有 `chat.inputQueue` 国际化资源。发布前需由 Admin Drizzle 提供队列和任务关系 capability，并验证 Dream 可调用；尚未发布时服务端拒绝写入，页面保留草稿，不能用临时内存队列绕过持久化。

## 验收场景

1. Agent 正在输出时连续提交两条正文：两张卡片按服务端顺序出现在 Dock 上方，草稿分别只清空一次；当前输出不中断。
2. 点击某条卡片的删除或“关闭排队”：只移除该条，另一条留在队列；刷新后结果一致。
3. 从菜单编辑一条 `queued` 消息并发送：旧条不再被消费，新条按服务端顺序排队；提交失败保留编辑稿。
4. 从菜单打开侧边聊天：只创建一个独立 Thread，首条输入为选中正文，原 Thread 不消费该消息；刷新可重新读取侧栏状态。
5. 点击“调整方向”：界面先显示服务端确认的选中状态；中断失败、owner 丢失或结果不明时不显示“已消费”，也不自动重发。
6. 模拟队列读取不可用、提交明确失败和提交结果不明：三种反馈可区分；草稿保留；失败态没有假排队卡片；重试同一提交标识不会产生重复消息。
7. 在宽屏、侧栏展开、窄屏和浏览器缩放下检查：Dock 右侧始终只有一个发送或停止按钮，切换前后都完整可点；卡片、错误和输入主列对齐；菜单不越过视口；键盘与读屏能找到当前动作。
